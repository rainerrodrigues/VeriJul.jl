Waiting for events

@tick waits a fixed number of clock cycles. That's enough for the filter, which always answers one cycle later, but many designs take as long as they take: a divider, a bus that inserts wait states, a state machine waiting for input. A testbench for them has to wait for something to happen, not for a number of cycles.

This tutorial uses examples/gcd.v, which computes the greatest common divisor of two numbers by repeated subtraction. You pulse start; busy is high while it works, and done pulses for one cycle when result is ready. How long that takes depends on the numbers.

using VeriJul

dut = load_dut(joinpath(pkgdir(VeriJul), "examples", "gcd.v"), "gcd"; build_dir=mktempdir())
sim = Simulator(dut)
start_clock!(sim)
reset!(sim)
dut
DUT(gcd, 8 ports)
  input   clk              1 bit
  input   rst              1 bit
  input   start            1 bit
  output  busy             1 bit
  output  done             1 bit
  input   a                16 bits
  input   b                16 bits
  output  result           16 bits

A small helper starts a computation:

function start!(sim, a, b)
    sim.dut.a = a
    sim.dut.b = b
    sim.dut.start = 1
    @tick sim
    sim.dut.start = 0
end

Waiting for a condition

@wait_until checks a condition now and after every rising edge, and returns once it is true. Its result is the number of edges it waited:

start!(sim, 48, 18)
cycles = @wait_until sim dut.done == 1
(cycles, dut.result)
(9, 0x0006)

Different inputs take a different number of cycles, which is why counting cycles with @tick wouldn't work here:

start!(sim, 1000, 3)
cycles = @wait_until sim dut.done == 1
(cycles, dut.result)
(339, 0x0001)

The condition can be any Julia expression, for example @wait_until sim dut.busy == 0 && dut.result != 0. If it is already true, @wait_until returns 0 without waiting.

Always set a limit

If the design never gets there, because of a bug or a missing start, an unbounded wait hangs the test. Pass max_cycles and a WaitTimeout is thrown instead. Its message quotes the condition and says when it gave up:

@tick sim                                           # let the last `done` pulse end
try
    @wait_until sim dut.done == 1 max_cycles=50     # nothing was started
catch err
    sprint(showerror, err)
end
"WaitTimeout: `dut.done == 1` did not happen within 50 cycles (gave up at time 4020, cycle 403)"

timeout is also available, as a wall-clock limit in seconds, the same as for tick.

Waiting for a signal edge

wait_edge waits for a port to change. For 1-bit ports, edge is :rising (the default) or :falling; :change works for ports of any width. It returns the port's new value:

start!(sim, 12, 8)
wait_edge(sim, :busy; edge=:falling, max_cycles=100)
(dut.done, dut.result)
(0x01, 0x0004)

sim.cycle counts rising edges of the main clock, so it can measure how long something takes:

dut.a = 255; dut.b = 15; dut.start = 1
wait_edge(sim, :busy)                  # the design accepted the request
dut.start = 0
c0 = sim.cycle
wait_edge(sim, :done; max_cycles=1000)
(latency = sim.cycle - c0, result = dut.result)
(latency = 19, result = 0x000f)

wait_edge samples the port after every evaluation of the design, that is after each edge of any clock, which is when outputs change.

The function form

wait_until is the function behind @wait_until. It takes the condition as a function, which reads well as a do block when the condition is longer than one line. It also takes clock and edge, so it can check on another clock's edges:

start!(sim, 81, 27)
wait_until(sim; max_cycles=100) do
    dut.done == 1 && dut.result > 0
end
dut.result
0x001b

Which one to use

To wait for…Use
a fixed number of cycles@tick sim n
a condition on one or more signals@wait_until sim cond max_cycles=…
one signal to rise, fall or changewait_edge(sim, :port; edge=…)
a condition that spans several lineswait_until(sim; max_cycles=…) do … end

All of them work inside @testbench tasks, and the clock waits for them in lockstep like it does for @tick.
